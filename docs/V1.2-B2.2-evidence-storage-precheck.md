### 凭证处理优先顺序

1. **优先采用有自动刷新能力的运行临时身份。** 为应用限定目标桶及 `study-evidence/production/` 前缀，验证凭证过期后无需人工重新部署。官方 SDK 文档描述了云托管的默认鉴权及函数型云托管的 context 方式，但不能直接推导当前 Docker/FastAPI 服务已经具备 Python COS 可用的凭证供应器。[CloudBase SDK 鉴权](https://docs.cloudbase.net/api-reference/webv3/initialization)
2. 本地 CLI 的临时凭证、桶策略里的 TCB 服务主体，都不是已经交付给生产容器的应用身份。当前 adapter 只读 SecretId/SecretKey/可选 SessionToken，没有刷新逻辑；静态塞一组短期 token 不算解决方案。
3. 如果当前托管形态无法提供适用的运行身份，备选是**专用、最小权限 CAM 子身份密钥**，但需要业务单独接受长期密钥维护责任。凭证由有权人员放入腾讯云控制台的云托管服务版本环境变量，不进入 Git、Dockerfile、管理端或小程序。限制配置读取权限，并制定轮换/撤销流程；不使用主账号密钥。[云托管凭证配置入口](https://docs.cloudbase.net/recipes/secure-secrets-in-cloud-function)
4. SSM 可作为后续凭据托管选项，但本轮没有核实已开通实例、费用和运行读取身份，因此不把 SSM 当作现成免费能力，也不为它另起一套架构。

## 4. 上传、查看、路径及图片安全

继续沿用以下链路，不让业务层接触 SDK：

```text
小程序 → 后端身份/岗位/组织/草稿状态校验 → 图片解码与重新编码
      → 预留不可见 metadata → 私有 COS 新对象 → 激活 metadata + audit

运营后台 → plans:read + 本班范围校验 → 后端读取并核对 SHA/大小 → 临时响应图片
```

当前代码已有：

- 每场至多一张有效合影；只允许在 DRAFT 上传/替换，提交后不开放随意替换。
- 5MiB 输入/处理后输出限制；识别 JPEG/PNG、MIME 一致性、完整解码、像素上限、拒绝多帧和解压炸弹。
- 重新编码像素，丢弃 EXIF/GPS 和尾随数据；图片二进制不写 MySQL。
- 文件键为 `study-evidence/<env>/<session_id>/<随机UUID32位>.jpg|png`，没有姓名、手机号、member_code 或班组名称。session_id 不是秘密，安全依赖随机对象名与鉴权，不能依赖隐藏路径。
- 严格路径正则、环境和存储 namespace 核验；对象名只能由后端生成。无需为了换成年/月路径重做模型。
- 管理端 `GET /api/v1/study-meetings/records/{session_id}/evidence` 返回 `private, no-store`、`nosniff`，访问记审计，不返回永久 URL。

上线前补齐：COS PUT 明确禁止覆盖同名对象；增加上传次数、频率和在途数量限制，避免“一张有效合影”被反复替换刷成大量收费对象。5MiB 仍采用单次 PUT，无需分片上传。COS 的禁止覆盖请求头受版本控制状态影响，应在目标桶实测，不用启用永久历史版本来替代。[PUT Object 语义](https://intl.cloud.tencent.com/ind/document/product/436/7749)

**优先后端代理查看**，沿用现成权限和逐次审计。如果以后改短签 URL，建议60～120秒且不超过剩余有效期，不进入普通日志/数据库；需接受签名在有效期内可转发的风险。本轮不引入该分支。已被用户下载或截图的图片无法通过云端删除撤回。

## 5. 上传/替换的事务与补偿

DB 与 COS 不存在共同事务，不能用一次 SQL rollback 宣称两边原子成功。

| 阶段/故障 | 安全处理 |
| --- | --- |
| metadata 预留失败 | 不调用 COS PUT；原合影不变 |
| metadata 成功、COS 上传失败/超时 | 新记录保持不可见，标记待清理；不能显示“已上传”。超时按“对象可能存在”处理 |
| COS 成功、激活事务失败 | 不切换当前合影；保留新 key 的回收线索，尽力删除新对象，失败交由重试 |
| 替换成功 | 在同一个 DB 事务中停用旧记录、激活新记录、写 audit；提交后再异步删除旧对象 |
| 替换失败 | 不提前删旧对象；旧合影继续可用 |
| 删除成功、DB/audit 提交失败 | DB 保持待清理，下次重复删除；只有云端删除成功或确认对象不存在后才写完成标记 |
| 删除403/网络失败 | 不标记物理删除成功；有限重试并告警，继续处理其他对象 |

现有代码已具备“先预留、后上传、最后激活”的基础。还需验证超时后迟到 PUT、进程中断、并发替换、清理竞争：清理曾确认不存在，上传却随后完成时，不能永久漏掉新孤儿。采用有限上传总时限、失败即时补偿、周期性孤儿对账与前缀生命周期兜底；不能仅靠一次 NotFound 永久结束所有核对。孤儿对账只处理超过安全窗口、重新核对无有效引用的本业务对象，不扫描删除其他业务文件。
