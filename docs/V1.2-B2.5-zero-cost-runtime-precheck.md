## 3. 运行身份结论

当前 CloudRun 版本 `188` 的可见环境参数中没有：

- `TENCENTCLOUD_SECRETID/SECRETKEY/SESSIONTOKEN`；
- `CLOUDBASE_STORAGE_*`；
- `STUDY_EVIDENCE_*`。

这是“配置描述中未出现”的证据，不等于平台一定不会在容器运行时注入隐藏身份。当前 API 是容器型 FastAPI 服务，而不是带 `context` 参数的函数型 CloudRun 入口；尚未在实际容器内执行无敏感信息的 COS SDK 探针，所以不能把同环境运行身份标记为已验证。

官方文档说明事件型 Cloud Function / CloudRun 的 CloudBase Server SDK 可以读取运行时临时身份；当前 Python 适配器使用 COS SDK，需要确认该身份在容器中以 `TENCENTCLOUD_*` 或等价供应器可用，并且权限只覆盖目标 Bucket 的必要对象操作。[CloudBase SDK 鉴权](https://docs.cloudbase.net/en/api-reference/webv3/initialization)

运行身份必须按以下顺序确认：

1. CloudRun 同环境临时身份（可自动刷新）；
2. 已批准的短期凭证供应器；
3. 只有前两者不可用时，才讨论最小权限 CAM 子身份及云端安全注入。

本轮没有创建 CAM 用户、没有生成长期密钥、没有把任何凭证写入 Git、前端、小程序、数据库或报告。

## 4. 工程实现

### 4.1 platform-api 受保护入口

新增：

```text
POST /api/v1/internal/study-evidence
```

请求体只允许：

```json
{"limit": 500}
```

保护规则：

- 必须提供 `X-Study-Evidence-Cleanup-Token`；
- Token 少于32个字符一律拒绝；
- 使用常量时间比较；
- 不返回 Token，不把 Token 写入审计或错误消息；
- 业务清理逻辑仍只在 `cleanup_evidence()` 中维护；
- 每批最多500条；单条失败不阻塞整批；
- production/staging 仍要求显式开启清理、CloudBase 后端、固定 `study-meetings/` 前缀和正常写入门禁。

当 `STUDY_EVIDENCE_CLEANUP_ENABLED=true` 时，应用启动还会强制要求服务端 Token 至少32个字符，避免“开关已开但服务身份为空”的半配置状态。

### 4.2 Cloud Function Cron 编排器

新增源码目录：

```text
cloudfunctions/study-evidence-cleanup/
```

函数只做以下事情：

```text
Cron
  → HTTPS POST platform-api 内部清理入口
  → 返回安全计数
```

函数不连接数据库、不实现过期判断、不操作 COS、不复制审计/幂等逻辑。所需服务端配置：

```text
PLATFORM_API_CLEANUP_URL=https://<approved-api-host>/api/v1/internal/study-evidence
STUDY_EVIDENCE_CLEANUP_TOKEN=<same-server-only-token>
STUDY_EVIDENCE_CLEANUP_LIMIT=500       # 可选
CLEANUP_REQUEST_TIMEOUT_MS=30000       # 可选
```

函数会拒绝非 HTTPS、非精确内部路径、带用户名/密码、查询串或片段的 URL，避免错误配置把清理 Token 发往其他地址。

根目录 `cloudbaserc.json` 已声明 `studyEvidenceCleanup`：

```text
functionRoot: ./cloudfunctions
dir: cloudfunctions/study-evidence-cleanup
runtime: Nodejs18.15
handler: index.main
trigger: timer
cron: 0 0 2 * * * *
```

该 Cron 是每天一次的模板。CloudBase 定时触发器使用七段 Cron；当前函数运行时内置时区说明为 UTC，正式部署前必须在控制台确认实际解释，避免把业务时间误当成北京时间。[CloudBase Cron 定时触发](https://docs.cloudbase.net/en/recipes/schedule-cloud-function-cron-job)

本轮**没有执行 `tcb fn deploy`，因此云端不存在这个新函数和触发器**。

## 5. 168小时、清理与补偿边界

- `uploaded_at + 168h` 是业务访问真相；到期后 API 立即拒绝查看，即使物理删除还未完成。
- 清理服务只扫描 `expires_at` 已过安全 grace 的 `study_meeting_evidence`。
- 只有 `study-meetings/` 前缀对象允许被删除。
- 对象不存在视为幂等成功；成功后写 `storage_deleted_at` 和审计。
- 业务记录、参加人员、课程、组织关系和积分不会被清理任务删除或重算。
- 上传替换保持“先上传新对象并验证 → DB 切换 → 再回收旧对象”；不会先删除旧照片。
- DB 失败时新对象进入补偿清理；旧照片继续保留。

## 7. 费用与批准门槛

当前代码和配置没有创建新资源，故本轮实际新增费用为 **0**。未来启用前仍需确认：

1. 每日一次 Cron 是否计入当前标准版已有的函数调用/CU额度；
2. 以每天1次、每批最多500条的上限估算，预计每月最多约31次清理调用（失败重试另计）；
3. 当前环境已有函数用量与 `EnableOverrun=true` 是否会让新增用量进入按量计费；
4. 控制台是否能设置合影清理的用量/费用告警；
5. 是否存在任何独立最低消费或必须购买的调度资源。

只要出现新增固定费用、无法确认费用上限、或运行身份需要未经批准的长期密钥，即保持：
