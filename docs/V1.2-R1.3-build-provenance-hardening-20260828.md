# V1.2-R1.3 Build Provenance Hardening

日期：2026-08-28（Asia/Shanghai）
仓库：`seiwajyuku-platform`
目标：`BUILD PROVENANCE READY`
范围：代码、镜像、CI 和发布清单机制；不执行生产部署

## 实施内容

### 1. API 只读 build info

新增 `GET /api/v1/system/build-info`，并保留两个只读兼容别名：

- `GET /build-info.json`
- `GET /api/version`

返回字段严格限制为：

```json
{
  "version": "...",
  "commit_sha": "...",
  "build_time_utc": "...",
  "build_id": "...",
  "image_digest": "...",
  "environment": "..."
}
```

缺少构建注入值时返回 `unknown`，不从运行环境猜测，也不返回数据库地址、密码、令牌或其他 Secret。

### 2. Docker provenance

根 `Dockerfile` 与 `Dockerfile.staging` 支持以下 build args，并写入同名运行时环境变量：

```text
APP_GIT_SHA
APP_BUILD_TIME_UTC
APP_VERSION
APP_BUILD_ID
APP_IMAGE_DIGEST
```

同时写入 OCI labels：

```text
org.opencontainers.image.revision
org.opencontainers.image.source
org.opencontainers.image.created
org.opencontainers.image.version
org.opencontainers.image.digest
com.seiwajyuku.build.id
```

本地或 CI 未连接镜像仓库时，`APP_IMAGE_DIGEST=unknown` 是明确的非发布状态；生产候选必须在镜像推送后用真实 `sha256` digest 生成发布清单。

### 3. 清洁源代码与发布清单工具

新增 [scripts/build_provenance.py](../scripts/build_provenance.py)，提供三个命令：

```text
verify    检查工作区干净、HEAD 与期望 SHA 一致；可选核对 origin/main
manifest 生成不可变 JSON release manifest
validate  校验 manifest 的 SHA、CI 结论、镜像 digest 和部署字段
```

CI 的发布候选门禁还会校验
`docs/V1.2-R1.1-migration-manifest-20260828.json`：清单中 0035～0042 的
MySQL/SQLite 正向与回滚 SQL 必须存在，且文件 SHA-256 必须与清单一致。
清单自身的 SHA-256 会写入 `release-manifest.json.migration_state`，将迁移
追溯基线绑定到每一次候选构建。

发布清单包含：

```text
schema_version
release_commit
source_tree_sha
version / environment
github_ci_run / github_ci_workflow / ci_conclusion
build_id / image_tag / image_digest
cloudrun_revision / deployment_time_utc / traffic_ratio
backup_id / feature_flags / migration_state
generated_at_utc
```

生产发布前可使用：

```text
python scripts/build_provenance.py verify --expected-commit <SHA> --require-origin-main
python scripts/build_provenance.py validate <manifest.json> --require-image-digest --require-deployment
```

`validate` 默认拒绝 `ci_conclusion != success`；`--require-deployment` 还会要求 revision、部署时间、备份 ID、0～100 的流量比例和真实 image digest。

### 4. GitHub Actions 门禁

`.github/workflows/ci.yml` 的 `api-container` job 现在会：

1. 检查 checkout 工作区干净且 HEAD 等于 `GITHUB_SHA`；
2. 用 `GITHUB_SHA`、构建时间、运行 ID和版本构建根 Dockerfile；
3. 检查 OCI labels；
4. 启动镜像并回读 `/api/v1/system/build-info`，核对 SHA、版本、构建时间、Build ID 和环境；
5. 不输出任何密钥。

新增 `build-provenance` job 仅在 `main` push 上运行，并等待所有 API、管理端、小程序、云函数、MySQL 集成和镜像 job 成功后：

1. 验证 `HEAD == origin/main == GITHUB_SHA`，并校验 R1.1 migration manifest 与所列 SQL 文件哈希；
2. 生成 `release-manifest.json`；
3. 校验 `ci_conclusion=success`；
4. 作为 GitHub Actions artifact 保留。

初始实现提交对应 CI：`33144457577`（`f6bf79874e5abbbe9cdc209ad243af1611e73b86`，`completed / success`）。
迁移清单哈希门禁收口提交为 `d13120f750fb289c132cbc86f5c3a614eda4acfa`，对应 CI：
`33145831282`（`completed / success`）。该次 CI 的镜像 job 完成 OCI label 与运行时
build-info 回读；`build-provenance` job 同时校验 0035～0042 的迁移文件哈希并生成
包含 migration manifest SHA-256 的 `release-manifest.json` artifact。

该 CI 清单是 CI 候选清单，不代表已部署到生产；未连接生产镜像仓库时 `image_digest` 保持为空，生产发布必须重新生成带真实 digest、revision、备份和迁移状态的清单。
