# V1.2 生产上线回滚方案

版本：R0  评审日期：2026-08-28
适用基线：`main@f3a041d6b032621a29590603c3f24f0dd4af834c`

> 这是发布前的受控回滚手册。优先关闭能力和回退应用，不把有损数据库 down 当作默认回滚。R0 当前未批准任何生产变更。

## 1. 回滚原则

1. 先止损：关闭对应 Feature Flag，停止 Cron/合影入口，阻止新增业务事实。
2. 再回退应用：API/管理端回到发布前已记录的稳定 revision 和构建产物。
3. 新增兼容表和可空列默认保留，不为追求版本号一致而删除。
4. 只有确认迁移本身造成问题、没有任何新数据依赖、并经过负责人批准，才考虑 down。
5. MySQL DDL 会隐式提交；任何“回滚”都必须基于实际结构核验和备份恢复方案，不能假设事务可以撤销 ALTER。

## 2. 按故障阶段处理

### 2.1 迁移前

- 未创建/未确认最新快照：停止，不执行迁移。
- 发现生产 `schema_migrations` 与对象不一致：停止，不重跑 ALTER；导出只读核验结果，人工决定续接点。

### 2.2 `0035` 或 `0036` 失败

- 立即停止后续编号。
- 读取 `schema_migrations`、`information_schema.tables/columns/statistics`，确认是“未创建、已部分创建还是记录未写入”。
- 因为新表尚无业务数据，优先修复后在受控窗口续跑；不自动删除半成品表。
- 若确需清理，先确认表为空、无引用，再由负责人批准执行对应 down；保留错误日志和备份 ID。

### 2.3 `0039` 或 `0040` 失败

- 先保持 `0035/0036` 已成功结构，不影响旧应用。
- `0039` 若目录表已建但种子未完整，按实际行数补齐，不重复覆盖运营自定义岗位。
- `0040` 若 ALTER 已成功但 migration 记录缺失，标记实际结构后补记录/修 runner，不盲重跑。
- `0040` down 只有在不存在 NULL `ends_at` 时才可讨论；禁止用虚假结束日期代替长期有效。

### 2.4 `0041` 或 `0042` 失败

- 关闭所有 V1.2 flags，保持旧 API/管理端运行。
- 若新表已创建但应用尚未切流，优先保留表，修复迁移或部署问题。
- 若 `0041` 已有课程/合影 metadata，或 `0042` 已有运营补录行，禁止执行 down；只能应用回退并保留数据。
- `0042` 的安全 down 仅在无 `added_by_user_id` 事实且经过计数核对后才可执行；脚本拒绝时不得绕过保护。

## 3. 应用发布失败

### API 失败

1. 立即关闭 `WECHAT_MEMBER_BINDING_ENABLED`、`STUDY_MEETING_SUBMISSION_ENABLED`、`STUDY_MEETING_EVIDENCE_ENABLED`、课程/人员修正开关。
2. 回退 API 到发布前已记录的稳定 revision（R0 现场为 revision 188，但发布时必须使用实际 digest/commit）。
3. 再检查四个健康接口和 V1.1.1 公开入口。
4. 保留新增结构；旧应用不应依赖新表即可恢复原业务。

### 管理端失败

- 先回退静态站点到发布前 build-info 对应的构建产物。
- API 和数据库保持不动；管理端恢复后只读查看，避免在版本不一致时执行修正写入。

### 小程序失败

- 不发布正式小程序；TEST 小程序停止使用新入口或恢复旧构建。
- 关闭身份绑定/学习会提交开关；已绑定记录保留，不删除 binding。
- V1.1.1 新学长申请仍应对未绑定用户可见，已绑定用户不应被强制回到申请流程。

## 4. 存储与 Cron 故障

### 运行身份或上传失败

- 关闭 `STUDY_MEETING_EVIDENCE_ENABLED`，禁止新的照片上传。
- 不删除旧照片；保留已激活 metadata，按补偿任务重试。
- 若 DB 已写预留但对象上传失败，标记预留记录逻辑删除并尽力删除孤儿对象；失败信息进入审计/告警。

### 替换失败

严格保持：

```text
上传新对象 → 验证新对象 → DB 切换 → 新对象生效 → 回收旧对象
```
新对象或 DB 切换失败时保留旧照片；旧对象回收失败不影响新照片，只进入可重试清理。

### 清理 Cron 失败

- 关闭 `STUDY_EVIDENCE_CLEANUP_ENABLED` 或暂停触发器，不影响 `expires_at` 的 API 拒读保护。
- 过期对象即便暂时未物理删除，也不得再被 API 返回。
- 修复后重复运行清理；对象不存在视为成功，`deleted_at/storage_deleted_at` 更新必须幂等。
- 不得让清理函数访问或删除 `study_meeting_evidence` 之外的表/前缀。

## 5. 数据库恢复与有损回滚判断

### 默认选择

优先使用：

```text
关闭 flags → 回退应用 → 保留增量结构 → 备份/PITR 仅在数据损坏时恢复
```
CloudBase/CynosDB 已有约 7 天 PITR 时间窗和可用整库快照，但恢复通常会生成新实例；正式恢复前需由数据库负责人确认停机/切换方案。

### 何时不得 down

- `wechat_member_bindings` 有正式绑定；
- `study_meeting_sessions/attendances` 有学习事实；
- `study_meeting_courses/evidence` 有课程或合影 metadata；
- `0042` 有运营补录（`added_by_user_id` 非空）；
- 岗位字典已被后台新增/修改；
- V1.1.1 新字段已有正式资料。

### 何时可以评估 down

仅当：

1. 已关闭所有相关 flags；
2. 业务负责人确认没有新事实依赖；
3. 已导出/核对受影响表和审计；
4. 已有可恢复快照；
5. 逐条执行 down 并核验，不使用批量强制删除。

任何条件不满足，都保留结构，采用应用回退或新修复迁移。

## 6. 回滚成功标准

- API 和管理端回到已记录的稳定 commit/digest；
- `/__tcb_probe__`、`/health/live`、`/health`、`/api/v1/health` 均 200；
- V1.1.1 新学长申请入口可加载，旧申请数据可读；
- V1.2 flags 全部关闭，Cron 不再产生写入；
- 没有新增积分、组织关系或真实学员照片损失；
- 所有回滚动作、操作者、时间、备份 ID、异常和最终计数写入发布记录。
