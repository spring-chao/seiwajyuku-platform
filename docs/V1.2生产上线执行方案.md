## 1. 发布范围与不变项

本次 V1.2 目标能力：

- 微信身份绑定，`member_id` 仍是业务主身份；
- 正式志工任职 → 岗位字典 → capability → 组织范围；
- 组长/辅导员登记小组学习会；
- 本组与同班跨组参加人员；
- 0～多门课程事实；
- 每场一张私有合影，业务保留 168 小时；
- 运营人员可修正课程和参加人员，修改有审计；
- CloudBase 内置云存储，固定 `study-meetings/` 前缀；
- 每日一次物理清理，不能绕过 `expires_at` 访问控制。

本次仍不启用：

- 学员正式积分结算（`LEARNING_CREDIT_SETTLEMENT_ENABLED=false`）；
- 生产二维码身份写入门禁；
- 未经单独批准的批量组织关系修改；
- 任何学习计划 B2 导入或发布；
- 正式微信小程序发布（仅使用 TEST 小程序做受控烟测）。

## 3. 0035～0042 逐项审计

> MySQL DDL 可能隐式提交；任何失败都先停下、核对实际结构和 `schema_migrations`，不能依赖 Python `rollback()` 恢复。

| 迁移 | 内容/旧表影响 | destructive 与 DDL 风险 | 重复检测、回滚与数据风险 | 锁与预计时间 |
| --- | --- | --- | --- | --- |
| `0035` | 新建 `wechat_member_bindings`，唯一约束 AppID+OpenID 和有效 member 绑定，FK 到 `members` | 不改旧表；首次建表/索引会有 DDL 元数据锁 | `IF NOT EXISTS` 可检测表；down 删除整表，存在绑定数据时有损；应只回退应用并保留表 | 新表为空时通常秒级；需短暂元数据锁 |
| `0036` | 新建学习会 session、attendance，两表 FK 到组织、周期和成员 | 不改旧业务表；FK/索引建表风险低，但依赖 `org_units`、`class_learning_cycles`、`members` | `IF NOT EXISTS` 可检测表；down 删除学习事实，有损，禁止有数据后执行 | 预计秒级；新表元数据锁 |
| `0037` | `members` 增加 8 个可空 V1.1.1 业务字段 | 修改旧表；MySQL `ALTER TABLE` 可能重建表/阻塞读写 | 无 `IF NOT EXISTS`；当前已应用，不能重跑；down 删除字段会丢新资料 | 约 1,238 行，预计秒级到分钟级，需低峰和锁监控 |
| `0038` | `members` 增加可空 `social_role` | 修改旧表；同上 | 当前已应用；down 删除党员社会角色资料，有损 | 预计秒级到分钟级，需元数据锁 |
| `0039` | 新建岗位字典、岗位 capability，并 `INSERT IGNORE` 11 个默认岗位/5 条能力 | 新表及种子；不改 `volunteer_appointments` | 表可检测；down 删除岗位定义/能力，可能丢后台新增配置；任职事实表会保留但失去目录解释 | 空表秒级；短元数据锁 |
| `0040` | 将 `volunteer_appointments.ends_at` 改为可空，NULL 表示长期有效 | 修改旧表；可能阻塞；当前表 0 行，风险低 | 无 `IF NOT EXISTS`；down 改回 NOT NULL，若已有 NULL 会拒绝，不能强行填假日期 | 空表通常秒级；需元数据锁 |
| `0041` | session 增加 `course_details_initialized`；新建课程事实和合影 metadata 表；种子课程修正权限 | 修改 `study_meeting_sessions` 并建表；合影/课程事实为新数据表 | down 删除课程/合影 metadata 和字段，明确有损且无数据保护；有数据后不得执行 | 依赖 `0036`；预计秒级到分钟级；需锁/外键检查 |
| `0042` | attendance 的 `added_by_member_id` 改可空，增加 `added_by_user_id`、FK、XOR check；种子参加人员修正权限 | 修改既有 attendance 结构；增加 FK/check，需扫描既有行 | down 已有运营补录时应拒绝；即使无数据也会丢列/权限，先回应用、再审慎 down | 依赖 `0036`；新表为空时短，仍需锁 |

**执行顺序：**由于 `0037/0038` 已存在，正式窗口不是盲跑 0035～0042，而是：

```text
预检对象与 migration 记录
→ 0035
→ 0036
→ 跳过已核实存在的 0037、0038
→ 0039
→ 0040
→ 0041
→ 0042
→ 每一步核验对象、权限、记录和计数
```

若某个 migration 记录缺失但对象已存在，先人工判定实际结构，不能直接重跑无 `IF NOT EXISTS` 的 ALTER。

## 5. 受控发布步骤（解除阻塞后）

1. 发布负责人确认新的备份/快照成功、可用、PITR 时间窗未中断，记录 backup ID。
2. 冻结并记录 API image digest、源 commit、管理端 build-info；确认可回退到 revision 188（或其实际稳定 digest）。
3. 再次只读读取 `schema_migrations`、目标表/列、权限和表规模；确认只处理缺失迁移。
4. 低峰期逐项执行 `0035 → 0036 → 0039 → 0040 → 0041 → 0042`，每步成功后立刻核验，不连续盲跑。
5. 发布与 R0 基线一致的 API，所有 V1.2 flags=false；健康检查 `__tcb_probe__`、`health/live`、`health`、`api/v1/system/environment`。
6. 在服务端注入内置存储 bucket/region/prefix 和最小运行身份；不将任何 secret 放入 Git、前端、小程序、数据库或日志。
7. 使用合成对象做 Put → Get → 替换 → 过期拒读 → Delete；确认对象路径仅为 `study-meetings/`，不返回永久公开 URL。
8. 部署 `studyEvidenceCleanup` 每日一次 Cron。时区以控制台实测为准；服务间鉴权只用云身份或安全配置中的高强度 token，超时 30 秒，单批最多 500。
9. 仅对内部测试 member/任职开启微信绑定；核验 binding 与 authorization 分离，且跨范围、过期任职拒绝。
10. 按顺序小范围开启 `WECHAT_MEMBER_BINDING_ENABLED` → `STUDY_MEETING_SUBMISSION_ENABLED` → `STUDY_MEETING_EVIDENCE_ENABLED`；课程/人员运营修正开关只在确认权限后再开。
11. 管理端执行人工验收卡；确认 V1.1.1 表单入口仍可用，且已绑定学员不再显示新学长申请。
12. 观察日志、5xx、存储失败、清理失败和资源用量；无异常后才进入下一步业务批准。

## 6. 发布后监控与停止线

- 任一迁移失败：停止后续迁移，保存错误和实际结构；不自动 down。
- API 5xx、健康检查失败、存储身份探针失败：关闭新增 flags，回退应用到稳定 revision。
- `expires_at` 访问限制失效、对象可公开枚举、错误跨范围读取：立即关闭 evidence flag，禁止真实照片继续上传。
- 计算资源达到 70% 提醒、85% 原因检查、95% 必须行动；`EnableOverrun=true` 下不得忽略费用告警。
- 所有生产烟测数据必须有 ID、负责人和清理/取消状态；不把测试申请转为正式学员，不产生积分。
