# AI 运营执行层 AI-1.0 至 AI-1.3V

## 目标

为企业微信、WorkBuddy 或其他 MCP 客户端提供一个受控的运营查询入口。Agent 通过领域 Service 的只读适配器取数，不直接访问业务数据库，也不重新实现 IAM、组织范围或续费/关爱规则。

本批次只验证：

`运营账号登录 → Agent 客户端认证 → Schema 校验 → 今日行动/查学长 → 脱敏上下文返回 → 全链路审计`

AI-1.3V 在 AI-1.3R 基础上补齐启动边界和标准 MCP 传输：本地开发允许显式启动初始化，staging/production 禁止应用启动自动迁移；MCP 改为官方 Python SDK 的 Streamable HTTP ASGI 应用，保留统一认证、组织范围、只读工具和审计边界。它不等同于 WorkBuddy 双用户身份委托验收。

写入、联系方式展开、导出、IAM 和批量操作不属于本批次。

## 安全模型

每次请求同时需要：

- 现有运营账号的 Bearer JWT，确定操作者和其有效角色/岗位；
- 独立 Agent 客户端 ID 与客户端密钥，确定调用方；
- `X-Agent-Channel`、`X-Agent-Session-ID` 和 `X-Request-ID`，用于当前阶段的调用标识和审计关联；Channel/Session 是调用方声明值，不是可信人员身份来源，也不能单独作为权限依据。

实际可用权限仍由既有人员权限、Agent 只读工具白名单和组织范围共同决定。`X-API-Key` 继续只服务机器到机器集成，不作为代人身份认证。

## 接口

### REST

- `GET /api/agent/v1/manifest`
- `GET /api/agent/v1/today-actions`
- `GET /api/agent/v1/members/search`（仅姓名检索；手机号参数会被拒绝）
- `POST /api/agent/v1/members/match`（手机号只允许放在 JSON Body）
- `GET /api/agent/v1/members/{member_id}/summary`
- `GET /api/agent/v1/members/{member_id}/timeline`
- `GET /api/agent/v1/members/{member_id}/renewal-context`
- `GET /api/agent/v1/members/{member_id}/followup-context`

### MCP Streamable HTTP

- `POST /mcp/seiwajuku`
- 使用官方 `mcp` Python SDK 的 Streamable HTTP transport，支持标准 `initialize`、`notifications/initialized`、`tools/list`、`tools/call`，并由 SDK 管理协议版本协商、`Mcp-Session-Id`、JSON 响应和 GET 事件流。
- 调用方必须发送 `Accept: application/json`；初始化后继续发送 SDK 返回的 `Mcp-Session-Id` 和 `MCP-Protocol-Version`。
- 应用层在进入 MCP transport 前验证 Bearer JWT、Agent client credential、channel 和 Host/Origin；每个 HTTP 请求重新建立运营账号上下文，不把 MCP session 或 channel 声明当作人员身份。

当前暴露的工具为：

`get_my_today_actions`、`find_member`、`get_member_summary`、`get_member_timeline`、`get_renewal_context`、`get_followup_context`。

所有工具都标记为只读；Agent 层没有写工具的路由，也没有调用现有写服务的旁路。

- MCP `tools/call` 使用与 manifest 相同的严格 Pydantic Schema，在进入领域 Service 前拒绝缺失字段、错误类型和额外字段。
- `AGENT_ALLOWED_TOOLS` 独立控制单个 Agent 客户端可暴露的工具集合，不能替代人员权限校验。

## 隐私边界

- 搜索结果和学员摘要只返回 `phone_masked`，不返回完整手机号；联系方式展开仍必须走原有 `contact:reveal` 任务机制，本批次不提供该工具。
- 姓名/手机号匹配只使用服务端手机号哈希完成比对；审计记录仅保存调用元数据、结果数量和请求标识。
- 关怀记录文本在进入 Agent 返回值前脱敏手机号和明确金额；今日行动仍复用现有聚合服务，避免生成新的事实口径。
- Agent 审计使用既有 `audit_logs`，并将 `agent_client_id`、`channel`、`session_id`、`tool_name`、`request_id` 写入审计元数据。
- 认证失败、停用账号、客户端工具拒绝、组织越权、非法参数、未知工具/方法和成功调用均进入审计；客户端密钥本身不写入审计。
- Agent 文本额外脱敏邮箱、手机号和明确金额；完整手机号不进入 REST Query String。

## 配置与发布门禁

默认 `AGENT_API_ENABLED=false`。启用前必须配置：

`AGENT_CLIENT_ID`、至少 32 位的 `AGENT_CLIENT_SECRET`、`AGENT_ALLOWED_CHANNELS`、`AGENT_ALLOWED_TOOLS`。

启动与发布边界：

- `.env.example` 和 dev Compose 默认 `RUN_BOOTSTRAP_ON_STARTUP=true`，只用于本地 SQLite 首次初始化；
- staging 示例显式为 `RUN_BOOTSTRAP_ON_STARTUP=false`，迁移和 IAM 初始化必须作为独立、可核验任务执行；
- Docker/production 默认关闭启动初始化；生产只读实例不执行应用启动迁移、IAM seed、业务写入或数据库迁移。

本批次不执行生产数据库迁移、不开放生产写入。AI-1.3V 代码级验收已覆盖：

1. Agent 查询通过 `members`、`renewals`、`followups` 领域 Service 取数；
2. 标准 Streamable HTTP 初始化、session header、工具列表和 JSON 响应均可用；
3. MCP 缺字段、错误类型、额外字段、非法 params 均返回协议错误或工具错误而不是 500；
4. 错误 Secret、非法 Channel、失效 JWT、停用账号、跨组织 member_id、工具白名单拒绝均 fail closed 并审计；
5. handler 适配器保持 ASGI lifespan，使 serverless warm invocation 也能运行 MCP session manager；
6. 本地 API 全量测试通过后，才进入 staging 双用户联调。

上线前仍需在隔离 staging 完成：

1. OAuth/连接器最终委托身份方案确认；
2. WorkBuddy 实际 MCP Streamable HTTP 握手和工具参数验证；
3. 同一 WorkBuddy Agent 下两名不同运营人员的双用户、双组织身份隔离验收；
4. 共享 Connector Credential 场景下禁止把 Channel/Session 声明当作人员身份；
5. 生产只读/写入门禁与回滚条件确认。

AI-1.4 之后再单独设计企微身份绑定；AI-1.7 之后再评审第一项 `create_followup_record` 写权限，并必须采用 Prepare → Confirm → Commit。
