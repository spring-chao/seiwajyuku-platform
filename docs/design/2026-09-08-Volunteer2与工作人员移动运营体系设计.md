# Volunteer 2.0 与工作人员移动运营体系设计

## 已确认的身份判断

| 身份 | 当前有效条件 |
| --- | --- |
| 学长 | `members.status = ACTIVE`（在册） |
| 志工 | 在册学长 + 当前有效的志工服务组织任职 |
| 专职人员 | 账号启用 + `operations_employments.employment_status = ACTIVE` + IAM2 角色×组织范围授权 |
| 小程序账号 | 可撤销的自然人微信绑定处于 `VERIFIED` |

`starts_at`、`ends_at` 对普通志工任职只保留为系统建档和结束操作的档案时间，不参与自动到期判断。学长转为非在册时，所有志工能力立即不可用；已结束或已撤销的岗位在恢复在册后不自动恢复。

## 志工服务组织

`volunteer_service_units` 是志工组织模型，包含体系、线别、上级服务组织、归属塾和服务对象正式组织。

- `parent_id` 表示治理/纵向组织路径；
- `service_target_org_unit_id` 表示实际服务的正式组织；
- 两者独立维护，系统不从班级或分中心名称推断；
- 任职的正式事实仍是 `volunteer_appointments`，V2 行通过 `volunteer_service_unit_id` 关联服务组织，并将服务对象同步保留在兼容的 `org_unit_id` 字段中。

岗位目录通过 `volunteer_position_profiles` 标注 `system_type`、`line_type` 与是否可新增。`volunteer_position_capabilities` 继续决定小程序服务能力；治理头衔本身不授予泛化后台权限。

## 多任职与推荐

同一在册学长可以有多条独立当前任职，不存在“主岗位”字段。推荐规则只配置来源服务组织/岗位到目标服务组织/岗位的候选关系；接受推荐时必须填写确认说明，系统才创建第二条独立任职和可审计的关联记录。不会因规则自动创建岗位。

`/api/v1/volunteer-management/migration-preview` 只展示基于已配置服务组织的唯一匹配、冲突和需人工核验项，不执行迁移或改写历史数据。

## 工作人员小程序

微信绑定升级为自然人绑定：`wechat_member_bindings` 可关联 `person_id`，工作人员首次使用移动端必须通过已有后台账号确认，得到的是独立、可撤销的小程序会话，而不是后台 JWT。

每次工作人员移动操作都会实时读取：

1. 账号是否启用；
2. 该自然人是否存在在职雇佣；
3. IAM2 `employee_authorization_grants → roles → role_permissions → org scope` 的有效状态。

移动端没有独立角色、组织范围或权限缓存。小程序只显示业务语言的工作台入口，服务层仍按每项权限的角色×范围精确计算。

## 边界

- Volunteer 2.0 任职不向旧后台 `volunteer_*` 角色投影；旧任职读取路径仅为兼容历史。
- 专职离职不会改变学长在册或志工任职档案；只是立即关闭专职移动运营能力。
- 本设计没有执行生产迁移、生产志工数据迁移、批量账号创建或生产发布。
