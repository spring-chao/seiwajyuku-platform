# 现行工程工作流

生效日期：2026-09-13。来源：用户批准实施 AGENTS、技能与 Workflow 审计建议。本文件管理工程执行，不改变业务规则、数据访问权限或生产写入开关。

## 与历史基线的关系

在系统与运行环境约束之内，先遵循用户当前明确范围，再遵循适用的 AGENTS.md 与本工作流。业务规则沿用 V1.1 及后续明确批准的专项决策；不能只按文件日期推断替代关系。

两份 V1.1 DOCX 保持原文与校验值。本工作流明确替代技术文档“执行边界”、18.1～18.3 及其他章节中重复出现的以下通用执行要求，也替代需求文档中同类普通发布要求：

| 历史执行条款 | 现行规则 |
| --- | --- |
| 每次只处理一个任务、一任务一分支一 PR | 分解可验收步骤并持续完成用户目标；提交保持聚焦，默认普通交付直接推送 main |
| 每次部署均重新回复“批准上线” | 已有效授权的普通发布不重复询问；新增生产数据、权限、迁移或费用动作另按授权表 |
| 所有任务都提交截图、迁移、数据核对、权限测试、费用与回滚全套材料 | 按影响提供相关证据；不适用项不制造材料 |
| 每次先业务 staging 验收、上线后固定观察 24 小时 | 保留实际发布门禁；按改动风险和明确验收要求确定环境、观察窗口及负责人，普通小改不自动增加人工等待 |

`docs/tasks/首批8个Codex任务.md` 及旧上线准备是历史任务记录。专项业务确认、敏感导出、人事任命、迁移及数据写入门禁不因以上替代而放宽。

## 授权表

授权记录应明确动作、对象、环境、范围；包含时间窗口时必须仍有效。范围变化、授权撤销或出现新的不可逆影响时，重新取得相应批准。工具审批配置和凭据可用性不等于业务授权。

| 动作 | 执行边界 |
| --- | --- |
| 相关代码编辑、只读检查、隔离测试、构建与发布准备 | 在用户任务授权内自行完成；不触碰用户无关改动 |
| 普通代码提交与推送 | 必要验证后直接推送 main；用户要求 PR 或实际保护规则要求时走对应流程；不强推、不绕过门禁 |
| 普通修复／优化的生产代码发布 | 沿用已确认默认发布授权，核验目标提交的 CI 与发布条件后继续；纯文档、技能、CI 调整无需重发生产应用 |
| 生产健康、版本等非敏感只读核验 | 在相关诊断／发布任务范围内进行，不将结果扩大为业务数据查询许可 |
| 生产业务数据查询、直接数据库连接或敏感导出 | 必须具有该访问方式、对象和数据范围的明确授权；优先有权限控制的最小化、脱敏接口 |
| 生产迁移、批量数据写入／删除、身份权限变更、密钥轮换、资源扩容 | 单独核验有边界的明确批准；先完成隔离验证、影响说明与恢复准备；不得由普通发布授权推导 |
| 联系外部人员、发送邮件／消息 | 仅在用户明确授权的对象和内容范围内执行 |

需要批准时只暂停依赖该批准的动作。准备具体差异、目标版本、验证证据和适用的恢复方案，再说明缺少什么批准及其规则出处。已有同范围有效批准无需重复征求。

## 验证矩阵

| 改动影响 | 所需证据 |
| --- | --- |
| 文档、AGENTS、技能 | 引用路径、适用范围、冲突检查；技能执行结构验证，不跑无关业务全套测试 |
| 测试入口、CI | 验证发现的测试集合、错误退出及工作流结构；运行受影响测试；远端结果以该提交的 CI 为准 |
| 前端行为 | 类型检查、相关行为测试；界面变化进行对应页面核验，构建变化验证构建 |
| API 业务行为 | 相关单元／集成测试；覆盖改动触及的失败路径 |
| 权限、隐私、组织范围 | 服务端越权、范围隔离和脱敏测试；源码匹配测试只能补充，不能证明运行时权限正确 |
| 数据库结构、导入与同步 | 隔离 MySQL 兼容性、前向迁移、幂等与数据核对、安全回滚／恢复验证；SQLite 不能替代 MySQL |
| 正式代码发布 | 目标提交 CI、构建来源、线上版本、健康、认证及受影响业务验证；容器还检查部署状态、启动日志和流量 |

本地按影响选择测试，当前 main CI 的完整门禁保留。相同代码与环境已通过的检查不机械重跑；外部状态变化或新证据使结果失效时再验证。禁止把未执行、失败、超时或待人工验收记成通过。

## 工具与上下文

从适用规则和相关文件开始；历史报告、DOCX 及记忆只读取相关部分。技能按描述匹配，引用按需展开。发布与数据库技能只在相应任务使用，不作为所有开发工作的前置流程。

独立只读工具调用可并行并检查每个结果；有依赖或共享状态的修改顺序执行。根据新证据诊断失败并选替代路径；执行中的工具返回会话标识时继续跟踪，不重复启动同一任务。写入结果不确定先核验实际状态。没有可行替代且缺少外部输入时，报告具体阻塞与已完成工作。

Windows 文件操作使用原生 PowerShell 和 LiteralPath；递归删除／移动前核验目标绝对路径。避免把读取的文件路径或内容拼接为跨 shell 命令。

## 测试入口与 CI 维护

- 管理端：`node scripts/run_node_tests.mjs admin-web`，或管理端目录 `pnpm test`。
- 小程序：`node scripts/run_node_tests.mjs miniprogram`。
- 用 `--list` 查看测试集合而不执行。入口扫描约定测试目录，并纳入 `scripts/test_*miniprogram*.mjs`，新增测试无需逐项改 YAML。
- B2 是手动专项验证，不合并或取消其生产隔离门禁。
- PR 可取消同一 PR 的过期 CI；main 发布证明不因新的提交而自动取消。
- 当前不添加路径跳过：未来若分流，必须覆盖共享依赖、锁文件、迁移、Dockerfile 与 CI 自身，并确保 `build-provenance` 仅在其要求的全部检查成功后产出。不可把 skipped 当成通过。

## 交付与恢复

交付结果包含结论、改动、实际验证及未完成事项。代码完成、已推送、CI 通过、部署提交、服务运行、业务验收分别依据实际证据报告。未达到用户目标时继续处理；外部阻塞时交付可审阅结果并说明缺口。

发布流程见 [普通代码发布](deployment/ordinary-release.md)。不为每个任务自动启动 24 小时监控；有明确观察要求时记录时长、责任人和异常条件，确需后续自动跟踪时使用受支持的自动化。

长期记忆不是任务完成条件；仅用户明确要求归档时按统一协议处理，未经核验的历史状态不作为当前事实。
