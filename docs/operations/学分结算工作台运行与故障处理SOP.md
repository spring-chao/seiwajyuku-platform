# 学分结算工作台运行与故障处理 SOP

状态：供代码评审与非生产验收；不能代替生产迁移、权限、开关或账本写入授权。

## 1. 适用范围

本 SOP 覆盖学分运营工作台及统一结算批次：小组学习会、班级学习会、每日读书、优秀分享和历史学分。`learning_credit_entries` 是正式事实账本，运营页面不提供直接编辑积分的能力。

批次数据库结构由迁移 `0067_learning_credit_settlement_batches` 管理。普通课程学分还依赖已批准的规则映射/绑定状态；历史导入另依赖 `0065/0066` 的 staging 与时间精度结构。每个环境的迁移状态必须实时核验，不能从代码、CI 或其他环境推断。

## 2. 权限与开关

批次读取和维护需要 `plans:credit_settlement_manage`；账本查询需要 `plans:credit_settlement_preview`。高风险动作使用独立能力角色：

| 角色 | 主要能力 | 限制 |
| --- | --- | --- |
| `credit_settlement_approver` | 独立审批 | 批次创建者不能审批自己的批次 |
| `credit_settlement_poster` | 已批准批次正式入账 | `RESTRICTED`；仅系统管理员可显式分配 |
| `credit_settlement_reconciler` | 对超时 `POSTING` 批次做只读账本核对并收敛状态 | 不需要正式入账权限；仍受对账恢复开关约束 |
| `credit_settlement_closer` | 核对已入账条目并封账 | 不编辑账本 |
| `credit_settlement_reverser` | 追加负向冲销记录 | `RESTRICTED`；仅系统管理员可显式分配 |

历史批次还需要 `plans:historical_credit_import_manage`。在后台「专职人员管理 → 编辑 → 学分结算专项能力」中，系统管理员可按角色和组织范围显式授予能力；每次新增、变更或撤销都必须填写授权原因并写入 IAM 审计。正式入账与冲销角色仅系统管理员可分配/调整，操作员不能为本人增加学分能力。岗位或普通负责范围调整会保留独立学分能力，不会静默撤销。身份写入门禁关闭时此入口只读。角色模板不会自动更改现有人员授权；生产权限变更仍需单独授权。

服务端分别使用以下开关，权限不会自动打开开关，开关也不会自动授予权限：

- `LEARNING_CREDIT_BATCH_DRY_RUN_ENABLED`
- `LEARNING_CREDIT_BATCH_APPROVAL_ENABLED`
- `LEARNING_CREDIT_BATCH_POST_ENABLED`
- `LEARNING_CREDIT_SETTLEMENT_ENABLED`
- `LEARNING_CREDIT_HISTORICAL_POST_ENABLED`（仅历史正式入账）

生产环境不得由本 SOP 或工作台自行修改开关。当前值应通过批准的只读运行时核验方式确认。

## 3. 标准操作流程

1. **确认范围与前置条件。** 核对目标来源、事实日期/期间、班级组织范围、规则版本和人员映射；确认所需 schema 已在目标环境通过正式迁移。对历史数据核对来源固定为 `LEGACY_SUZHOU_2026_V1`，保持原分值和原时间精度，不用当前规则重算。
2. **生成 DRY-RUN。** 选择来源记录或活动日期范围。此操作会创建批次及审计记录，属于数据库写入；它只冻结提案，不写正式账本。生产执行前需独立授权。若 feature gate 关闭或数据映射不完整，停止并保留 blocker。
3. **复核批次。** 对照就绪条数/分值、阻塞数量、重复数量、班级/期间、来源和规则指纹。详情只展示必要的脱敏信息；原始快照不应复制到工单或外部报告。阻塞项不能进入审批或 POST。
4. **提交独立审批。** 将冻结提案提交至 `PENDING_APPROVAL`。审批人重新打开批次核对指纹和明细；创建者本人不得审批。审批只改变批次/审计状态，不写账本。
5. **正式 POST。** 只有 `APPROVED` 批次、指纹/来源复核通过、权限与所有 feature gates 均通过时，才由获批的入账人执行。系统逐条入账并以稳定幂等键防重；成功后核对批次数、金额、items 与 ledger 一致。正式 POST 是不可逆业务写入，不能依据本 SOP 推定已获授权。
6. **处理部分失败或中断。** `PARTIAL_FAILED` 不会自动续跑；先打开批次并核对已入账条目。`POSTING` 只有在心跳至少 30 分钟无更新后，才可由对账恢复角色运行只读账本对账。若未标记入账的幂等键已经出现在账本、指纹变化或条数/分值不一致，立即停止并人工调查；不得盲目重试。
7. **封账。** 对 `POSTED` 批次核对提案数、提案金额、记录的已入账数/金额与账本逐项对应；一致后由封账角色将状态收敛为 `CLOSED`。封账不新增或修改账本行。
8. **纠错与冲销。** 已入账错误只能通过追加负向冲销记录纠正，必须说明原因；原记录保持不变。冲销记录不能再次冲销。随后建立新的更正批次处理正确事实，不得修改或删除原记录。
9. **学员查看。** 小程序仅基于已绑定的本人身份返回 `POSTED/REVERSED` 账本汇总和最近记录；DRY-RUN、待审批提案和历史 staging 不向学员展示。负向冲销会计入净分并明确标示来源。

## 4. 停止条件与故障处理

出现任一情况即停止当前批次，不扩大范围、不创建替代批次、不进行 SQL 手工修复：

- 来源事实、规则版本、组织范围或批准指纹与快照不一致；
- blocker 未解决、重复结果无法解释、学员身份/历史期间存在歧义；
- feature gate、权限、scope 或迁移状态与批准包不符；
- `POSTING` 状态过新、账本中出现未登记的幂等键，或批次与 ledger 对账失败；
- 小程序本人绑定身份不能唯一解析，或汇总/记录对不上正式账本。

记录批次号、状态、错误类别、时间、actor 和不含敏感明细的审计关联信息。不要在日志、工单或报告中记录 Token、密钥、数据库连接串或未脱敏个人资料。需要修复时先通过批次详情、审计日志和受控只读查询定位；状态未知不得重放 POST。

## 5. 发布前/后验收清单

代码与非生产验收至少包括：API 全量测试、MySQL 集成测试、权限隔离测试、幂等/并发/部分失败恢复测试、后台 typecheck/build、小程序测试与静态检查，以及 `0067` MySQL/SQLite schema 测试。

生产使用前须另行完成并授权：控制器/runtime provenance 与健康核验、目标环境迁移验收、角色分配审批、各 feature gate 核验、来源基线与账本前后不变量、备份/审计/恢复方案。任何一个缺项都不能将学分模块称为已生产启用。

每批结束至少记录：批次号与类型、来源/期间、规则指纹、就绪/阻塞/重复数、审批人、入账数/金额、冲销关系、ledger 对账结果、最终状态及审计引用。不得以页面显示成功代替账本对账。
