# 已确认累计学分作为期初余额

适用情况：现有学分已经由运营人员确认，现在需要把每位学长的累计值录入平台，供小程序展示。累计原值不重新按课程规则计算，也不计入本月或本年度的学习成绩。

## 运营人员操作

1. 打开“活动与学习 → 学分结算工作台”，使用最上方 Excel 导入入口。
2. 下载带学长名册的模板。系统填好编号、姓名、班级/分中心，不含联系方式。
3. 只填写“累计学分”：非负数，最多两位小数。空白表示本次暂不导入，已确认零分填写 `0`。
4. 选择这份累计分的统计截止日，上传填写后的 `.xlsx`，点击“检查 Excel”。
5. 如果出现错误，按表格中的 Excel 行号和解决方法修改，重新检查。姓名或班级不符时，先核对学员名册，不按同名或模糊匹配入账。
6. 检查通过后提交复核。学习条线专职人员查看每位学长的分值并确认，可以复核自己上传的文件。
7. 有入账权限的人员确认正式入账。已入账记录和期初余额总览会显示结果，小程序累计学分增加相同数额。

上传和提交复核不加分。按用户2026-10-10确认，上传人可以复核自己的文件，并兼任入账人；三个动作分别记录审计。系统管理员具有全部后台权限，学习条线专职人员获得专用的期初学分权限，权限范围仍绑定其现有组织授权。

重复上传、改文件名或改变数字显示格式不会再加分。每位学长只保留一份期初余额。截止日以前已有正式学分时，必须先核对重叠来源；后续日常结算也拒绝重复计入截止日覆盖的期间。

尚未入账发现分值错误，可以取消此导入，原来源和审核历史仍保留，再上传修正后的文件。已入账不能直接改原值或取消；应根据复核后的真实来源追加更正记录，技术人员需提供对应的审计和前向修复方案，不通过删除余额或修改截止日制造再次导入机会。

## 首次准备和恢复

`0069_learning_credit_opening_balances.sql` 增加独立的来源批次、来源行、期初余额三个表，并仅给既有学习专职角色 `employee_learning_management`、`ops_center_learning` 登记 `plans:credit_opening_manage`，与课程规则 `0064`、旧历史表 `0065/0066`、旧结算批次 `0067` 和推荐机构 `0068` 无依赖。不运行启动自动迁移，不改旧账本、课程规则或个人身份任命。

固定准备接口使用当前后台管理员身份，要求系统管理员角色及既有生产规则操作权限；运行代码提交和脚本 SHA256 必须与读取到的状态一致。发布配置需明确开启 `CREDIT_OPENING_SETUP_ENABLED`，运行仍受生产写入总门禁约束。接口没有任意 SQL、路径或表名输入。

接口先取得数据库操作锁、确认三个目标表及迁移标记均未存在，提交 `STARTED` 审计后才执行 DDL。MySQL DDL 隐式提交，异常后保留已完成结构和执行审计，不自动重试。刷新状态核验实际结果。成功只登记 `0069` 和完成审计；再次请求只返回就绪状态。未知或残缺结构拒绝再次执行，需检查差异后做单独的前向修复。

正式导入配置为 `LEARNING_CREDIT_OPENING_BALANCE_ENABLED`。人员权限由上述专用能力及现有有效角色、组织范围校验，也不改变既有日常结算、历史导入和 G5 规则应用的开关。

来源行按身份和范围检查，规范化内容指纹包含成员 ID、组织、名称、分值和截止日，不依赖文件名。提交、审批、入账都复核当前名册与重叠账本。正式入账在同一事务中完成全部余额和审计；每位学长唯一键防止跨文件重复。日常账本和期初入账在写入前都锁定成员行，避免并发时先前检查结果过期。

隔离 MySQL 测试涵盖实际建表、提交/复核/入账、重复、范围、半途写入回滚、DDL 中断后的持久拒绝重放，以及空表降级和非空来源拒绝降级。回滚脚本只允许三个表均为空的情况；任何保留的来源、审核或余额都阻止删表。非空生产数据采用前向修复，不能把整库回退当成学分纠错。

该路径解决已确认累计分的录入与展示。今后按课程、学习会等事实自动结算，仍需独立完成课程规则和日常结算的发布准备；不能用期初余额的可用状态声称自动结算已经完成。
