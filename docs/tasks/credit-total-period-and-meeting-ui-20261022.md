# 累计学分展示、读书批量入账和登记页面优化

## 问题与结果

汤会会截图中累计 339 分已存在，顶部取的是当前学习年度分数；年度配置缺失时用横杠代替，造成没有总分的误解。小程序现在把累计总学分放在首位，年度学分和待归属说明独立保留，不推定或改写年度归属。同类情况使用同一展示代码，覆盖累计为零、非零、负值和年度缺失的回归用例。未取得线上其他学长的实际受影响人数：已登录管理端浏览器读取超时，随后 Windows 工具因无法可靠识别浏览器网址停止。没有使用直接生产数据库连接替代。

读书入账使用有界批量 INSERT，一段事务内共用规则查询及期初余额查询，仍逐项验证冻结条目并链接每日账本。规则发布状态、退役绑定、权限、组织范围、来源指纹、期初截止日、学员锁和每日幂等键保持原有语义。保留每日事实而不把重叠期间变成不可拆分的单条累计事实；一人上传时段的累计分值继续在结算回执中汇总。已有重复键走原有严格字段比较，任一异常整段回滚，已提交段可续跑。

小组登记压缩班级/小组/周期卡片；跨组添加整行展示，确认按钮固定底部整行展示并适配安全区，保留选择、搜索及草稿行为。

## 验证

本地 API 相关测试 102 通过、1 项 MySQL 并发测试跳过；另补充自动结算的隔离 MySQL 并发测试，等待远端 CI 验证。249 分合成数据查询数 6067 → 3976（约减少 34%），每日账本仍 249 条，15 次有界请求，不能据此承诺生产耗时。多行插入后的异常及进程中断覆盖整段回滚；重传/日期重叠覆盖不重复计分。

小程序237项行为测试、配置检查通过；管理端101项行为测试、类型检查及 staging 构建通过。界面静态样式已检查；受工具停止影响尚未完成实际设备视觉验收。小程序上传开发版、微信审核及正式发布分别记录，不互相替代。

发布沿用普通代码发布授权，无迁移、无生产学分重放或批量业务数据修改。发布证据记录在统一 outputs 目录。


## 追加确认需求

- “我的学习”当前服务按班级 ID 只显示一个当前小组，沿用学员管理的主关系优先、最新关系其次；排除未生效、已过期关系，保留其他班级和历史学习事实，不执行生产关系清理。
- 用户明确要求：小组学习会人工核实后自动结算，不再到结算工作台操作。新增私有核实来源入账路径，复用冻结预览、正式账本、防重和回执；逐步重验核实指纹、来源关联、权限和组织范围。保留功能开关，不写入虚假的独立审批人。失败保留核实状态及实际已入账部分，可在原页面重试；进程中断保留原有30分钟对账门禁。仅在确认请求中触发，不在列表/详情读取时写账，不自动回放历史生产记录。
- 用户更正月度口径：当月基础满分=发布工作日读书天数×1+优秀检视分享5+班会和空巴18+小组会4。取消对班级排期和课程满分的依赖，最新发布日历必须覆盖整月并包含调休，否则待配置。分子只计当月四类已入账净分，排除期初和其他课程/活动，并扣除同类冲销。仍保留全部新增/累计学分原值。
