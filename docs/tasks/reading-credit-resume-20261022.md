# 读书来源重复提交与入账进度

用户反馈：200行读书原表入账时页面未完成返回，最初显示已入账65分，稍后重新打开已显示173/173分；两个来源行显示同一173分，难以判断是否重复加分。来源备注按用户明确要求改为选填。

## 原因与边界

- 原确认接口在一个请求内顺序处理全部日期及人员；每人入账前重复校验整份日期预览，来源详情还逐行访问数据库。页面超时不能证明事务失败，后端可能继续执行。用户后续截图与此路径吻合；未取得该次浏览器网络错误文字，不把具体网关错误码作为已证事实。
- 来源指纹原来含必填说明。同一文件改说明会新增来源回执，但事实ID、结算及账本幂等键可以共用，因此两条来源显示相同已入账总分不能相加。
- 读书账本已有学员ID与日期的唯一幂等键。修复保留该约束、逐条原子事务、实时事实/规则核验、权限及组织范围。

## 修改

- 来源备注选填、不参与新回执的计分指纹；保留旧指纹校验兼容。备注仍与文件一起归档，编辑备注不再作废已检查的计分预览。
- 同一文件、绑定、选项、有效行的重复上传返回已有来源；改名或更改备注不新增来源。历史相同来源且关联同一组结算的列表行合并展示次数，保留原记录。
- 新客户端每次确认最多处理3条、约8秒后在条目边界保存进度，客户端顺序续传；保持一条账本事实和关联状态同事务提交。单条事务不会被强制时间截断。
- 正常分段返回原待确认状态和实际已入账笔数，不伪造复核。暂停、刷新或断线后继续原结算，已入账条目不重算；已部分入账的来源不得重新生成并替换冻结条目。
- 来源详情按集合校验事实及签到，减少逐行数据库往返；处理中详情显示已提交条目实际进度。
- 界面区分正在入账、继续入账、已完成入账；失败信息在弹框内保留。响应丢失先查实际状态，不自动重发不确定写操作。
- 遗留中断状态使用现有对账恢复接口逻辑，保留对账权限、组织范围及30分钟无心跳限制，只核对账本，不在恢复操作中加分。

## 验证与发布

隔离用例覆盖备注省略/空白/单字的HTTP上传与确认、重复文件、不同文件重叠日期、分段暂停续传、旧重复来源合并展示、空闲恢复权限与时间限制、单次批量读取事实。管理端行为测试覆盖连续步骤、响应丢失但后端完成、响应不确定时不自动重发、暂停和选填备注。

生产核验只使用版本、健康、认证及最小请求日志元数据；未为真实学长重复入账、修改余额或删除来源。生产数据不因代码发布自动清理。最终提交、CI及发布回执另存本任务outputs目录。

## 同次追加的签到需求

团队报名姓名一致时允许扫码确认本人签到，签到引擎实现与验证位于signin组件的`docs/named-team-self-checkin-20261022.md`。主平台同步调整当天公开活动元数据：允许显示已结束/已关闭但仍为确认举办的场次，可签到场次优先；取消与草稿仍不公开。小程序仅可打开open场次，未开放与已结束显示对应提示。管理端团队提示改为姓名一致可扫码确认，未扩大人工签到权限。

## 追加核查：保存来源连接失败

用户的新截图在“保存来源”阶段提示无法连接学分接口，312行原表已检查完成；这与上述确认入账中断属于不同阶段。截图不能确定 Axios 超时、网络中断或网关错误码，最小请求日志元数据也没有该次可关联的失败回执，不能把具体传输原因写成已证事实。

核查发现原保存入口仍逐行重复查询权限、期初结构、班级关系、学习绑定和规则，并逐条保存事实及来源行。用相同的26人×12天、312条隔离合成数据对比：`3999d27` 保存执行9,683次SQL调用，追加修复后686次（约减少93%，包括每条事实的审计）。该数字是调用量对比，不是生产延迟承诺。

- 校验阶段一次读取班级关系、期初截止日、已有来源事实；学习绑定、规则和日历仅在本次预览内复用，保存与正式入账仍重新核验。
- 新增事务内批量事实写入，复用原单条事实的字段校验，逐次请求验证权限与组织范围；分块保存事实和来源行，逐条事实审计保留，整份来源与事实同事务提交。
- 保存响应丢失或5xx时先用受权限和班级范围控制的只读接口查询指纹。查到已提交来源即打开原记录；未查到或查询失败保留检查结果，不自动重传。保存已成功、仅明细读取失败时明确提示“来源已保存”。
- Axios `ECONNABORTED`/`ETIMEDOUT`单独提示响应超时及结果待核验，避免混同无法连接。来源备注继续选填，不改变计分身份。

验证：67项来源及活动事实API测试、21项管理端行为/错误提示测试通过；涵盖312行批量保存、逐条审计、重试无重复事实、来源事务回滚、权限/范围/受控来源/绑定/非法分值拒绝、跨请求关系重新校验和只读查询权限。类型检查与构建通过。MySQL兼容以目标提交CI的隔离MySQL结果为准。浏览器隔离页尝试遇到工具连接重置，未把它登记为页面验收成功；没有回放真实用户上传。
