# 组织身份与志工体验代码审计

- 审计日期：2026-07-29
- 范围：`seiwajyuku-platform` 当前本地代码与仓库内非生产验证库
- 生产边界：未连接、读取或修改生产数据库；未查询真实账号姓名、手机号或人员归属
- 结论：现有模块具备组织范围、角色有效期和审计基础，但缺少独立自然人、雇员、岗位、志工任职及用户主体语境，不能直接据此迁移真实人员。

## 组织模型

`migrations/*/0001_iam.sql` 的 `org_units` 以 `SZ_ROOT` / `org-suzhou` 为根。SQLite 只允许 `ROOT`、`REGIONAL_CENTER`、`CLASS`、`GROUP`、`SPECIAL_COHORT`；MySQL 虽没有数据库枚举约束，应用语义仍使用同一组类型。

当前根节点名为“苏州塾”，没有“盛和塾总部 → 江南塾 → 苏州分中心”的正式上级层级，也没有“运营中心”机构类型。六个三级分中心、班级、小组和特殊班属于学长组织树；把运营中心塞入该树会混淆专职机构和学长组织。

本地非生产验证库只出现上述旧组织类型。不得据此推断生产组织现状。

## 人员与身份

| 当前实体 | 当前语义 | 缺口 |
|---|---|---|
| `app_users` | 登录账号，可选 `member_id` | 账号与自然人未独立；外键语义不完整 |
| `members` | 学长主档及主三级分中心 | 会员年度身份未独立，不适合承载雇员或志工 |
| `member_org_relations` | 学长的主中心、班级、小组、特殊班、发展关系 | 可以表达学长多组织关系，不能表达专职机构归属或志工任职 |
| `user_roles` | 账号永久或定期角色 | 没有任命依据、任职组织、状态和可解释授权来源 |
| `data_scope_grants` | 账号的 ALL/SUBTREE/UNIT 范围 | 与岗位或任职分离，任职失效不一定同步撤权 |

仓库内没有可靠的“真实人员是专职还是志工”映射来源。姓名、手机号、旧角色和图表“所属分中心”都不足以自动认定身份；真实迁移只能输出待确认候选。

## IAM

`apps/platform-api/app/services/iam.py` 已按有效期过滤 `user_roles` 和 `data_scope_grants`，并把多角色权限合并；`accessible_org_ids()` 支持 ALL、SUBTREE 和 UNIT。

主要问题：

- `operations_admin` 同时拥有组织维护、全局 MP 导入发布、学长资料、企业敏感资料、关怀、审计、集成、续费和签到权限，明显宽于单一专职岗位。
- `regional_manager`、`class_counselor`、`group_leader` 是账号角色，角色名称把真实志工任职永久化；其范围和角色虽可分别设置期限，但没有共同任职来源。
- `system_admin` 是宽业务角色；尚无“不自动获得业务敏感数据”的纯技术管理员模板。
- `get_member_detail()` 和企业资料服务仍按角色名判断，无法解释权限来自雇员岗位还是志工任职。

## 前端路由与语境

前端 `router/modules/seiwajyuku.ts` 可以用角色隐藏菜单，路由守卫也会检查角色；服务端 API 同时检查权限，因此没有仅靠菜单隐藏。

但前端没有“运营中心专职端 / 志工端”主体语境。`followups.vue` 将“创建关怀任务、责任人、截止时间、关闭任务”等文案硬编码在页面；同一账号多重身份时也没有可审计的展示依据。需要集中字典和明确的语境选择规则。

## 底层工作项

- 关怀使用 `followup_tasks`，字段包括 `assigned_user_id`、`due_at`、状态和保密范围；服务层和异常文案大量使用“任务/责任人/关闭”。
- 续费使用 `renewal_cycles`、`renewal_followups` 等独立实体，当前前台栏目为“续费运营”。
- 签到异常没有统一工作项实体，主要通过签到裁定、同步和数据质量记录处理。

底层实体可以保持稳定技术命名，前端应按用户主体适配显示。现场扫码签到链路不在本轮改动范围。

## 兼容结论

1. 使用纯新增身份与任职表，不修改 `members`、签到事实表或现有账号授权记录。
2. 旧角色继续兼容读取；新授权优先从有效雇员岗位或志工任职派生。
3. 运营中心雇员权限来自岗位；对三级分中心的访问来自单独服务责任范围，不构成组织归属。
4. 志工权限由任职名称、组织范围、状态和起止时间共同决定。
5. 技术管理员采用独立模板，默认不含学长、联系方式、企业或财务查看权限。
6. 旧角色迁移只生成候选和异常，不直接写生产。

## 旧角色风险分类

| 旧角色 | 可能的新语义 | 自动迁移 |
|---|---|---|
| `operations_admin` | 运营中心负责人或某一专职岗位 | 否，岗位需业务确认 |
| `regional_manager` | 理事、三级分中心负责人或其他区域志工 | 否，任职名称、范围、任期需确认 |
| `class_counselor` | 班主任、班委等班级志工 | 否，具体任职及任期需确认 |
| `group_leader` | 组长、组委等小组志工 | 否，具体任职及任期需确认 |
| `system_admin` | 技术管理员，也可能兼有业务身份 | 否，必须拆分授权目的 |
| `data_security_admin` | 数据安全职责 | 否，不能等同技术管理员 |
| `read_only` | 临时观察或审阅用途 | 否，需要用途和有效期 |
