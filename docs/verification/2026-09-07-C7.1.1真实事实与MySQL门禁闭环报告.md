## 1. 真实 C7 事实接入结论

已建立独立检查表：[C7.1.1真实C7事实接入检查表](2026-09-07-C7.1.1真实C7事实接入检查表.md)。当前盘点结果如下：

| 事实 | 当前已确认的统一平台生产入口 | 历史候选来源 | 当前状态 |
| --- | --- | --- | --- |
| 每日读书 | 无 | `member_activity_facts` 中来自 `reading_checkins` 的历史承接记录 | `DATA_NOT_AVAILABLE` |
| 优秀分享 | 无 | `member_activity_facts` 中来自 `reading_shares` 的历史承接记录 | `DATA_NOT_AVAILABLE` |

现有 C7 事实登记 API 只是受权限保护的事实保存能力，不代表业务入口已经接入。旧系统历史活动代码虽然定义了 `reading_checkins`、`reading_shares` 的字段映射，但旧系统活动事实只读预检曾记录这两类来源均为0；该历史报告不能替代本次对当前生产状态的重新核验。

因此本阶段没有从生产取得样本，也没有在隔离库人为拼装“真实样本”。取得首批真实事实后，必须保留来源稳定 ID、学员稳定身份、正式班级、发生日期和发生日期所属的唯一学习轮次，复制到隔离库后逐条 DRY-RUN，并由运营人员100%复核。

## 2. 跨数据库 C7 业务签名

为避免 SQLite/MySQL 仅比较数据库自增 ID，新增共享业务签名校验，比较以下稳定语义：

- 发生日期、`READY/NO_CREDIT/BLOCKED` 状态和拟得分；
- 日历年份/日期类型、规则键/规则版本、优秀分享自然月；
- 每日读书业务幂等键；优秀分享幂等键中的数据库事实 ID 规范化为 `<fact_id>`。

同一隔离样本的 SQLite C7.1 测试和 MySQL 专项均断言同一稳定签名：

```text
每日读书：2026-01-05、2026-01-04、2026-02-14 为 READY +1；
          2026-01-01、2026-01-11 为 NO_CREDIT；
          2027-01-01 为 BLOCKED / BUSINESS_CALENDAR_MISSING；
优秀分享：2026-05 前5次 READY +1，第6次 NO_CREDIT / MONTHLY_CAP_REACHED；
拟结算：每日读书3分，优秀分享5分。
```

实现位置：

- 稳定签名：[c7_1_1_parity.py](../../apps/platform-api/tests/c7_1_1_parity.py)
- SQLite 同构断言：[test_c7_1_business_calendar_reconciliation.py](../../apps/platform-api/tests/test_c7_1_business_calendar_reconciliation.py)
- MySQL 迁移/回滚/同构专项：[test_c7_1_1_mysql_reconciliation.py](../../apps/platform-api/tests/test_c7_1_1_mysql_reconciliation.py)
