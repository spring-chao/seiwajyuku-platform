## 2. Adapter 架构

固定业务操作：

```text
G5_4_RECONCILE_COURSE_RULES_2026
```

共同 service：

```text
apps/platform-api/app/services/production_operations.py
apply_g5_4_course_rule_reconciliation()
```

两个薄入口：

```text
Mode A: POST /api/v1/ops/production-actions/g5-4-course-rule-reconciliation/apply
Mode B: scripts/apply_g5_4_course_rule_reconciliation.py
```

HTTP endpoint 设置 `include_in_schema=false`，普通 OpenAPI 不展示；请求模型 `extra=forbid`，不存在 `sql`、`statement`、`query`、`table`、`raw_command` 或客户端自定义锁名。CLI 只解析相同业务门禁参数并调用同一 service，不直接实现另一套写库逻辑。

## 3. 为什么 CloudBase RunSql 不满足事务边界

CloudBase RunSql 的每次调用是独立请求，无法保证多个请求复用同一个 MySQL connection，也无法让本地进程跨请求持有同一个 `BEGIN/COMMIT/ROLLBACK` 上下文。把 `SELECT → UPDATE/INSERT/DELETE → final SELECT` 拆成多次调用会产生可见的中间态，并使失败注入无法整体回滚。

platform-api 已使用 PyMySQL `autocommit=False`。Adapter 在一次 service 调用中获得单个 connection，由 `transaction()` 从事务开始持有到 commit/rollback 与连接关闭，因此全部重读、锁、业务写入、审计和最终校验处于同一数据库事务。

## 5. Release commit 与双 fingerprint

请求必须传入 40 位 `expected_release_commit`。服务从现有 build provenance (`APP_GIT_SHA` / baked build-info) 读取当前运行 commit，并在取得业务锁后再次核对；不一致返回：

```text
RELEASE_COMMIT_MISMATCH
```

事务内重新加载 `data/learning-plans/course-credit-rules-2026.json` 并重算 canonical fingerprint；同时从数据库重读版本和全部生产规则并重算 production fingerprint。请求指纹必须分别等于实时值，否则返回：

```text
PRODUCTION_FINGERPRINT_MISMATCH
CANONICAL_FINGERPRINT_MISMATCH
```

代码未把 C3.1 的两个运行值写成常量。

## 6. 单连接事务与固定数据库锁

MySQL 使用固定锁：

```text
seiwajyuku:g5.4:course-rule-reconciliation:2026
GET_LOCK(..., 0)
```

锁名不能由客户端修改。拿不到锁返回 `APPLY_ALREADY_RUNNING`。锁随唯一数据库 connection 在 commit/rollback 后关闭而释放，避免“先释放锁、后提交”的窗口。SQLite 使用同进程 non-blocking 等价锁，仅用于本地测试。

MySQL 事务使用 `SERIALIZABLE`，目标版本、规则、通用规则和 ledger 读取采用同 connection 的 locking read；commit 前再次读取规则和 ledger。
