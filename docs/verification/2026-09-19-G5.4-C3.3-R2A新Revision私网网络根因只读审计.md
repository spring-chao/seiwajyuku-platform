## 6. “5% 健康通过”不能证明命中 256

可回读的 `256` DeployRecord 使用 `TrafficType=FLOW`；当前发布单的 `TrafficType=FLOW` 且 `UrlParam`、`TrafficTypeValues` 均为空。此前健康请求使用服务默认域名，没有附加 URL 参数或定向 Header；没有 request log 或 revision response header 能证明某一次 `/health` 由 256 响应。

因此：

```text
5% 灰度阶段 /health=200
不能证明 256 成功连接生产 MySQL
```

这只是随机百分比分流下命中稳定版本 `253` 的可行结果。之前 100% 流量下 256 的 `/health` 和 `/api/v1/health` 为 500，仍与缺少私网网络配置相吻合，但本报告不把 5% 结果当作 candidate DB 证据。

以后候选验证应使用 `URL_PARAMS` 或 `HEADERS` 定向到 candidate，稳定版本保留为默认路由；本轮不实施灰度配置修改。

## 8. 根因分类与最小未来修复建议

```text
结论 = A / REVISION_VPC_CONFIG_NOT_INHERITED
```

排除项：

- 不是 B：MySQL 没有绑定窄范围安全组；默认安全组也不是旧 Pod IP 白名单。
- 不是 C：没有同时发现 VPC 配置正确但安全组阻断的证据。
- 不是 D：service `InternalAccess=close`、公共访问配置和 `TrafficType=FLOW` 在稳定/候选共用；现有证据直接落在版本级 VpcConf 丢失。

未来最小修复方向（本阶段不实施）：

1. 修复部署工具/发布流程，使每次新 revision 从当前稳定 revision 或完整 service 配置继承 `VpcConf`，而不是手工为某个 257 填一次 VPC。
2. 在发布前增加版本级断言：目标 revision 的 `VpcId/SubnetId/VpcCIDR/SubnetCIDR` 必须与稳定 revision 一致；不一致则禁止切流。
3. 将健康验证改为 URL 参数/Header 定向 candidate，并记录可证明 revision 命中的请求证据。
4. 不建议开放 `0.0.0.0/0:3306`；本次未提出安全组变更，因为 DB 当前无绑定安全组且根因已由 VpcConf diff 充分解释。
