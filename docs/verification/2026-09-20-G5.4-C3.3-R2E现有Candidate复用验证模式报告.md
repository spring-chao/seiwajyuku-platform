# G5.4-C3.3-R2E 现有 Candidate 复用验证模式报告

日期：2026-09-20（Asia/Shanghai）  
阶段：代码、测试与文档准备；不执行生产验证。

## 结论

R2E 新增了一个与普通发布路径隔离的 `VERIFY_EXISTING_CANDIDATE` 模式。它接收一个已存在的 revision（例如 `seiwajyuku-platform-api-257`），只做严格只读预检；获得另行批准并以 `--execute` 运行时，唯一允许的控制面写入是一次 `ReleaseGray` 的 `TrafficType=URL_PARAMS` 定向路由，随后一次 `ReleaseGray` 的 `TrafficType=FLOW` stable=100%、candidate=0% 恢复。

本阶段未向腾讯云发送生产 API 请求，没有创建或修改生产 revision，没有设置生产路由，没有连接或写入生产数据库，也没有进入 R3。SDK 请求结构仅在离线测试中验证。

## 控制器与运行时 provenance

```text
R2D_BASELINE_COMMIT = 4231b77c9b69a36216e22f2bc6f4f61e87afb475
CONTROL_TOOL_COMMIT = 执行时显式传入包含R2E功能的获批main完整SHA
EXPECTED_CANDIDATE_RUNTIME_COMMIT = 4853e709952beb6abc306abb0303eba59be5d30a
```

开发基线与未来实际控制器提交也分别记录：旧 R2D 提交不含本次 R2E 功能，不能冒充执行版本。candidate runtime SHA 只用于定向 build-info。

正式执行必须提供 `--controller-release-manifest`。代码检查实际脚本所在 checkout 干净、HEAD=获批控制器SHA=远端main、manifest commit/tree 相符；通过 GitHub 只读查询验证本仓库 CI 工作流的 main push 已完成，九个预期 job 全部 success。缺少 manifest、脏 checkout、错误 tree/SHA/分支/工作流、少 job、失败或 skipped 都拒绝。candidate runtime manifest 不能替代控制器证明。

## 新模式边界

```text
--verify-existing-candidate <revision> --dry-run
    只读预检，不产生任何写调用

--verify-existing-candidate <revision> --execute
    需要 --approval-ref、--expected-stable-revision、--control-tool-commit、--controller-release-manifest；重新只读预检后，才允许：
      1. ReleaseGray / URL_PARAMS / stable=100 / candidate=0 / 一次性 sj_canary
      2. 23 个定向探针（2 build-info + 1 liveness + 20 DB health）
      3. SearchClsLog 只读身份门禁：candidate=23, stable=0, unknown=0
      4. ReleaseGray / FLOW / stable=100 / candidate=0 恢复
```

模式明确拒绝普通 artifact 参数、环境变更参数、灰度比例和 FULL promotion。它不会调用 `UpdateCloudRunServer`、`SubmitServerConfigChangeDiff`、`StartVersionInstance`、`StopVersionInstance` 或 `DeleteCloudRunVersions`，也不实现 `OperateServerManage`。

## 只读预检门禁

1. 读取并确认服务 `normal`、`TrafficType=FLOW`、唯一 100% stable、无活动 release order、无运行中的 manage task。
2. 读取指定 candidate 的 `DescribeVersionDetail`；candidate 缺失、名称不符、状态非 `normal` 时返回 `EXISTING_CANDIDATE_NOT_REUSABLE`，绝不创建替代版本。
3. candidate 普通 FLOW 必须为 0，否则返回 `EXISTING_CANDIDATE_TRAFFIC_UNEXPECTED`。
4. candidate 四项 `VpcConf` 必须逐字段等于 stable，否则返回 `CANDIDATE_VPC_MISMATCH`。
5. `G5_4_PRODUCTION_RULE_APPLY_ENABLED`、`LEARNING_CREDIT_SETTLEMENT_ENABLED`、`RUN_BOOTSTRAP_ON_STARTUP` 必须在 candidate `EnvParams` 中显式为 `false`，否则返回 `EXISTING_CANDIDATE_GATE_UNSAFE`；模式绝不修改环境。
6. 只读记录 stable runtime commit、candidate expected runtime commit 与 controller provenance。

## 定向验证与失败关闭

定向路由必须轮询 `DescribeReleaseOrder`，实际观察到 `TrafficType=URL_PARAMS`、stable/candidate 身份、stable 默认优先级、candidate 非默认优先级和一次性 token 完全一致后，才允许发出 HTTP 请求。路由未激活返回 `CANDIDATE_ROUTE_NOT_ACTIVE` 且探针数为 0。

候选实例只读观察 `DescribeCloudRunPodList` 并等待正常冷启动。超时返回 `CANDIDATE_INSTANCE_NOT_READY`；只有明确平台证据表明必须显式启动时才使用 `EXPLICIT_CANDIDATE_START_REQUIRED`。不把超时当作该证据，也不调用 `StartVersionInstance`。

正式路由前重新运行只读预检，拒绝计划生成后的环境或稳定版本漂移。`ExistingCandidateSdkApi` 在 SDK 请求分发层拒绝所有创建/修改/删除、实例启停、OperateServerManage 与源上传操作，仅允许所需读 API 和 URL_PARAMS/恢复0% 的 ReleaseGray。恢复时还检查发布单的 FLOW、空 TrafficTypeValues 与空 UrlParam；残留 token 不算恢复。恢复请求不确定时不盲目重发，失败输出 cleanup evidence；失败路径也读取发布单和任务状态。closed 必须有明确终态，unknown 不算通过。

任何身份、liveness、DB health 或 CLS 门禁失败都会尽力恢复 FLOW stable=100%、candidate=0%，随后停止。恢复后只读报告 `TRAFFIC_RESTORED`；发布单是否关闭单独报告 `RELEASE_ORDER_CLOSED`，不猜测“取消灰度”的 `OperateType`。
