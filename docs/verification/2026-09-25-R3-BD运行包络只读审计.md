# R3 B/D运行包络只读审计

范围：用户批准只读收口B/D方案；本轮未查询或修改生产业务数据，未部署、未改环境、未调用APPLY。依据固定478fe6ce版本的scripts/deploy_cloudrun_api.py。

## 结论

BD_EXECUTION_ENVELOPE_READY=NO。现有普通发布器不能直接当作受限的R3启用/关闭工具。用户对R3业务APPLY的确认不包含本报告发现的额外控制面动作。

## 已核实的真实动作序列

普通execute(promotion=full)的成功路径：

1. UpdateCloudRunServer一次，ReleaseType固定GRAY。
2. ReleaseGray(URL_PARAMS)一次，确认定向路由、candidate实例、HTTP健康及CLS身份。
3. ReleaseGray(FLOW, gray_percent)一次；默认5%，不是零普通流量。
4. ReleaseGray(FLOW, 100%)一次。

共4个显式SDK写调用。发生异常且_routing_changed=true时，最多另尝试一次ReleaseGray(FLOW,0%)恢复，成功路径与失败路径不能混算成固定“仅两次操作”。本统计是控制器显式调用数，不保证SDK底层不存在重试。

execute成功路径只检查全量build-info和health，没有再证明IsReleasing=false或管理任务终态；不得把该返回结果当作发布单关闭。

## D阶段特有风险

若B已将true版本晋升为stable，D部署false版本失败时，现有_best_effort_restore_stable_route会恢复D开始时的stable，即APPLY=true版本。这符合普通可用性回退，但不符合R3关闭开关的失败安全要求。禁止直接复用普通失败恢复并声称开关已关闭。

新false版本100%也不自动证明旧true实例已经停机、无定向/直接入口可用；需要独立读取真实实例、路由、发布单状态。

## 配置与镜像边界

build_update_request显式传递镜像、完整EnvParam与VpcConf四字段，ReleaseType=GRAY。它没有对全部实例规格、出站策略等作逐字段继承断言；必须针对实际请求与版本详情核对，不把“只改一个env”当作全部配置不变的证明。

stable-image取服务OnlineVersionInfos的ImageUrl；“镜像URL”或tag相同不等于已验证不可变digest。批准前必须取得258的确切image reference与摘要并证明平台支持该引用方式。不得重新编译镜像代替复用。

## 推荐待实现/核验的最小专用路线

- 保留258（false）作为固定安全基线。一次创建临时true候选，仅URL_PARAMS定向，不经普通FLOW灰度、不把true晋升为默认。所有R3请求必须携带定向条件，且此前已用实例及CLS证明命中临时版本；runtime commit相同不能替代revision身份。
- B只有候选创建1次、定向路由1次的目标额度；任何失败不创建第二个候选。B后先设硬检查点，用户/执行计划确认就绪才允许单次C。
- C仅既有受控HTTP endpoint一次，禁止重试不明响应；事务内重读校验。
- D不以“开关改回false”触发另一轮不必要的普通发布作为默认设计。目标是恢复258普通100%、彻底取消本次临时灰度并使true版本不可服务；必须先证明官方控制台取消该发布单的精确语义、目标与运行实例最终状态。
- 因取消灰度可能保留true配置的离线revision，还须明确关闭标准：在线进程/可路由端点均false且true版本不可启动复用，还是要求保存的版本配置也false。若要求后者，需要额外独立获批的版本清理/禁用机制，当前无已证实路径，不擅自授权删除。
- 恢复路由和关闭发布单必须分别验收。未知OperateType不得猜；需要人工控制台语义动作的步骤应明确列为人工检查点。

上述路线避免把true版本作为D失败回退目标，是架构建议，不是已存在可执行命令。现有--promotion ready会在验证后自动恢复路由，不能在C前保持受控会话；--verify-existing-candidate又要求G5=false。因此不应通过关闭这些门禁或临时调用内部方法拼装执行。
