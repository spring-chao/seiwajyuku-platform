# 学分运营与学员查询跨模块隔离验收

代码起点：main `2497bae05eadc6b451609aa4221cc0e8f26bf6e8`。本项增加跨模块测试和 CI 入口，并根据真实隔离 MySQL 失败修复审计 Decimal 序列化；不改变权限、安全开关或迁移脚本。

## 验收目的

不能以批次服务、运营汇总、小程序查询各自的单元测试推定整条链路可用。新增 `test_credit_lifecycle_acceptance.py`，让这些模块在同一隔离账本上工作，并核对真实查询 API 返回。

### 小组学习会链路

创建学习会事实、上传合成照片、通过真实提交服务；使用测试冻结规则生成 DRY-RUN 批次。确认提案尚未出现在学员账本、审批不写账本、创建人不能自审。独立 reviewer 批准后 POST 并重放，核对无重复入账；封账不增加账本。

运营组织范围内的两个学员合计 8 分，绑定学员只能看到本人 4 分，另一学员的 entry detail 返回 404。本人记录冲销与幂等重放后，原行所有字段完全不变、只追加一条负数：运营净分变为 4 分，本人净分变为 0。详情保留冲销关联但不泄露审核原因。

### 历史导入链路

从合成 Excel 注册 staging，显式设置合成测试匹配结果和班级映射，并经过 YEAR 精度接受操作；MONTH/YEAR 分成批次独立审批、入账、封账。DRY-RUN 和 staging 均不出现在学员正式记录中；POST 后原值 1 分及 4 分保持不变，合计 5 分。

运营汇总和绑定学员 HTTP summary 同为 5 分；历史记录保持 `LEGACY_SUZHOU_2026_V1`，只显示“2026年1月”或“2026年”，不重新匹配当前规则或虚构具体日期。这里不验收真实生产 Excel 或自动人员匹配算法。

## 隔离与覆盖限制

- 本地在标准隔离 SQLite 测试环境执行；CI 的既有一次性 `study-meeting-mysql` job 明确加入同一文件，必须从 exact-head 结果确认 MySQL 证据。
- 测试只在进程内启用 feature gates，模拟结算能力和组织 scope；不授予真实 IAM 角色。真实 IAM 授权及隔离由既有专项测试和后续获批环境验收负责，不能由本项推断生产人员已具备能力。
- 学员绑定和 summary/history/detail 使用真实 TestClient 路由和会话；运营列表/汇总、审批入账/封账/冲销调用真实服务。
- 非真实浏览器、小程序设备或生产上线验收。未部署、未运行生产 DB 查询、APPLY、迁移或正式 ledger 写入；未创建 IAM 身份/密钥。

## 当前结果

第一次 exact-head CI `36750814085` 的 `study-meeting-mysql` 为 74 PASS / 1 FAIL。新验收在冲销环节发现 MySQL 驱动返回 `Decimal('4.00')`，`audit._audit_json_default` 仅支持日期，不支持 Decimal，导致审计序列化异常、业务事务回滚。SQLite 返回普通数值，因此原本地结果没有暴露此问题。该失败不跳过、不作为 PASS，也不推断生产已执行失败冲销。

修正：仅对有限 Decimal 使用精确十进制字符串（不经过 float）；NaN/Infinity 与未知对象仍拒绝。嵌套日期及既有 None 语义保持不变。新增精度、非有限值、未知类型与真实审计写入回归；完整冲销链路必须在新 exact-head MySQL CI 重新通过，不能以序列化单测代替。

新增两条跨模块链路本地 PASS；连同既有账本和学员查询回归共 32 PASS（`test_credit_lifecycle_acceptance.py`、`test_learning_credit_ledger.py`、`test_wechat_credit_history.py`、`test_wechat_learning_summary.py`）。远端 CI 以本次交付收口记录为准；代码测试通过不意味着生产激活完成。

生产路径仍需：受限只读采集身份和可信签封材料、合法的独立 DB 读取授权/通道、实时基线、当次控制器 provenance、规则 APPLY 及每项迁移/历史 staging/审批 POST 的单独批准、备份恢复与正式环境验收。

## 补充：重叠入账请求的真实连接验收

在同一测试文件加入两个线程、两个执行者的批次入账验收。第一执行者通过真实服务将所有权提交为 `POSTING` 后，只在首条 item 事务开始前暂停；第二执行者在独立数据库连接中调用同一个正式入账服务，必须因批次正在处理而拒绝，且账本不增加。释放第一执行者后必须完成恰好两条、合计 8 分的入账；第二执行者随后显式重放必须幂等，两个 item 对应两个不同的 ledger ID 和幂等键。

测试不模拟状态写入、不替换数据库连接或账本插入，也不以 sleep 猜执行时序。它验证已取得所有权后的重叠请求拒绝，不宣称覆盖两个事务在所有权 CAS 前同时竞争，或不同批次间月度上限竞争。原有 MySQL job 已包含此文件，无需改变 CI 入口。

本地三个 lifecycle 测试通过（SQLite，退出码 0）；退出清理仍出现既有 Windows `pytest-current` 权限警告，不删除共享临时目录。补充 MySQL 结果必须以新提交的实际 CI 为准；此前 main 的绿色结果不覆盖本次新增测试。
