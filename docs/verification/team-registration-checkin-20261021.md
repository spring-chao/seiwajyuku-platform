# 独立报名被误判团队、绑定后无法签到

用户要求排查 2026-10-20 活动中后台有报名、扫码及绑定后均无法签到的现象，明确本次不进行生产部署。本次依据截图及两组件源代码完成隔离复现，没有查询真实报名、连接生产数据库、补写签到或修改历史记录。

## 形成机制

签到组件 `spring-chao/signin` 的 `isTeamRegistrationSlot` 原先将“同一公司有多条报名＋该行缺少平台学员 ID/编号”视为团队名额，即使不同报名行姓名不同。`event_detail` 据此生成 `is_team`，管理端再显示“团队名额”；不代表操作人员明确创建了团队代报名。截图中“活动报名”下面同时出现“团队名额”与该推断规则一致；个案完整导入来源未读取生产数据核实。

扫码姓名查询会排除被判定为团队的记录，因此已存在的普通报名也可能显示未查到报名。绑定后，历史报名又只在已有学员 ID/编号、或姓名＋有效手机号核实成功时匹配；缺手机号会直接跳过匹配，故绑定身份成功并不意味着报名匹配成功。

## 修复

- 同公司不同姓名的普通报名不再判为团队。保留明确团队角色，以及同企业、同联系人、同联系方式重复占位的旧团队判断。后台提示改为“请先核对实际参加人”，去掉对不存在的小程序团队入口的误导。
- 原有报名导入仍要求姓名＋手机号才能关联学员身份，不进行姓名自动批量关联。
- 仅在已认证绑定后的本人签到核对中，允许空手机号的既有普通报名，由平台核验完整姓名在有效学员中唯一，且 ID、学员编号与已绑定身份均一致后匹配。有效手机号仍走原有核对；非空错误手机号不被忽略。同名多人、无效身份、已有冲突关联、真实团队及不存在报名均不猜测。
- 查询不创建报名、不写签到、不关联身份。确认时重读报名，事务内校验姓名、原身份及团队角色是否变化，既有原子写入防止重复渠道／并发重复计签到。
- 无须改小程序包。平台 API 须与签到组件修复配套；未来发布应先更新兼容新字段的 API，再更新签到组件。本次不执行这些发布动作。

## 验证

合成场景包含同企业不同姓名、空手机号、扫码报名选择、绑定原生授权、12 次并发确认、跨渠道重复签到、人工签到、真实团队、缺失报名与同名歧义。平台身份、服务鉴权、隐私及签到 API 相关测试 30 项通过；签到组件集成、课程、接口、原页面、导入、隔离包与事务测试结果以交付回执为准。管理端相关 24 项、小程序回归及类型检查通过。

真实活动签到现状保持不变，代码修复不等于相关学长已补签，也不表示生产问题已消失。
